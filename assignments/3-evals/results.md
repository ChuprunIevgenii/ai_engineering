## 4. Висновок (2–3 речення)

Чи B справді кращий за A? Чи різниця вимірна, чи це шум? Де B досі слабкий?

B не кращий за A: за суддею він навіть гірший (judge pass 0.10 проти 0.30), але інтервал містить 0, тож на 20 кейсах це не вимірна різниця. Code grader каже протилежне (0.75 проти 0.55), бо B частіше вживає потрібні слова — «sorry», «refund», «replacement» — але саме ці слова він вживає у зайвих обіцянках: код бачить форму, а не зміст. Головна слабкість B — обіцянки грошей і заміни без перевірки (55%) та вигадані факти (65%), а також обидві атаки через фальшивий авторитет.

## Prompt C *(опціонально)*

**Що змінили відносно B і на який тип провалу цілились?**
Залишили теплоту B (співчуття, вибачення, наступний крок), але додали правила з картки TechStore під кожен тип провалу: варіанти (заміна, повернення) лише умовно, після перевірки командою (`over_promise`); не називати цін, дат, гарантії, правил (`invented_specifics`); не писати «вже перевірив / надіслав» (`fake_action`); не обіцяти строків (`promised_timeline`). На dev перша версія C стала надто обережною — на все відповідала «передам команді» і не давала порад (d04, d05 fail, pass rate 0.80). У фінальній версії додали: завжди називати умовний варіант, коли клієнт питає про гроші чи заміну, і давати загальні кроки для технічних проблем (dev pass rate 1.00).
