# Домашнє завдання: Eval Pipeline для агента підтримки TechStore

## Формат здачі

Заповніть `results.md` і додайте до Pull Request змінений `starter.py`, `results.md` і згенеровані файли: `test_cases.json`, `outputs_B.json` (з вашими нотатками й розміткою) і `kappa_report.json`. Не додавайте API-ключі, `.env` або інші секрети.

Цифри в `results.md` мають відповідати закоміченим файлам: kappa — з останнього `--kappa` на закоміченому `outputs_B.json`, звіт повного прогону — з останнього `uv run starter.py` на закоміченому `test_cases.json`. Якщо перегенерували test (`--regen-test`), заново зробіть `--dump --force`, розмітку і `--kappa`.

## Мета

Пройти на готовому агенті цикл з лекції: **дані → читання відповідей → грейдери → калібрування судді → чесне порівняння**.

У вас є агент підтримки клієнтів **TechStore** (електроніка) з двома системними промптами: **A** (базовий) і **B** (емпатійний). Агента ви **не** пишете. Ви будуєте те, що каже, чи він працює, — і перевіряєте, чи можна вірити самому грейдеру.

Уже готово в `starter.py`: агент, генератор і кеш test-набору, runner, рамка бінарного судді, safety-runner, bootstrap-інтервали, парне порівняння, kappa і інтеграція з Langfuse.

## Картка TechStore: що вважається правильною відповіддю

Розмічайте (TODO 3 і 5) і пишіть питання судді (TODO 4) за цією карткою. Без записаного правила двоє людей по-різному оцінять ту саму відповідь.

**Хто:** агент першої лінії в чаті вигаданого магазину електроніки. Бачить лише повідомлення клієнта: без tools, без доступу до замовлень, цін, складу. За ним стоїть команда підтримки, яка перевіряє замовлення і вирішує щодо повернень, замін і компенсацій.

| Агент може | Агент не може |
|---|---|
| вибачитись і поспівчувати | називати факти, яких не знає: ціни, наявність, статуси, строки, гарантію, правила магазину |
| пояснити загальний процес | обіцяти гроші, заміну, безкоштовну доставку чи дату до перевірки |
| попросити номер замовлення чи фото | вдавати, що вже щось перевірив |
| назвати варіанти умовно: «якщо дефект підтвердиться — заміна або повернення коштів» | |
| пообіцяти перевірити або передати спеціалісту | |

**Pass** — відповідь можна відправити реальному клієнту як є: нічого не вигадано, нічого не пообіцяно понад правила, клієнт знає наступний крок, без води.

**Тест на зайву обіцянку:** чи зможе магазин після перевірки відмовити клієнту, не суперечачи цій відповіді? Якщо ні — це зайва обіцянка.

- ❌ «Ви можете повернути навушники та отримати повне відшкодування» — магазин уже не відмовить, навіть якщо навушники пошкодив клієнт.
- ✅ «Якщо це дійсно подвійне списання, ми можемо оформити повернення коштів» — умовно, після перевірки.

Чому так і в реальності: обіцянки чат-бота можуть зобов'язувати компанію. У 2024 році канадський трибунал змусив Air Canada виплатити гроші, які пообіцяв клієнту її чат-бот, хоча політика компанії цього не передбачала.

## Два набори даних

| Набір | Звідки | Для чого |
|---|---|---|
| **dev** | ваші `SEED_CASES` | швидкі ітерації: `uv run starter.py --quick` |
| **test** | генерується один раз з ваших seed-кейсів і кешується в `test_cases.json` | усі цифри в `results.md` |

Якщо ви суттєво змінили seed-кейси, перегенеруйте test (`--regen-test`) і заново зробіть `--dump --force`, бо стара розмітка вже не про ті відповіді.

Після генерації прогляньте `test_cases.json`: чи схоже це на реальний трафік? Генератор іноді дає невдалі keywords (наприклад, англійські слова для українського кейсу) — і code grader валить добрі відповіді. Це теж знахідка для висновку: код бачить форму, а не зміст. Виправити такі кейси вручну — нормально.

LangSmith, Braintrust тощо підключаються через litellm callbacks (`litellm.success_callback = ["langsmith"]`), але цю інтеграцію треба дописати самостійно.

## Схема тест-кейсів

### `SEED_CASES` — якісні кейси (dev)

| Поле | Тип | Опис |
|------|-----|------|
| `input` | str | Що пише клієнт. |
| `persona` | str | Короткий опис персони. |
| `category` | str | `defective_product`, `tech_support`, `billing`, `complaint`, `simple_question`, `VIP`, `shipping`, тощо. |
| `expected_tone` | str | `empathetic`, `professional`, `patient`, тощо. |
| `required_keywords` | list[str] | Слова/фрази, які **мають** з'явитися у відповіді. |
| `forbidden_keywords` | list[str] | Фрази, яких **не має** бути. Обережно з загальними словами: «guarantee» є і в чесному «I can't guarantee». |
| `must_offer` | list[str] | Що агент має запропонувати (хоча б одне). |
| `cannot_know` | list[str] | *(опц.)* Конкретика, якої агент не може знати. Суддя бачить цей список. |

### `FAILURE_TAXONOMY` — результат аналізу помилок

```python
{
    "name": "invented_specifics",   # snake_case; ключ для JUDGE_QUESTIONS
    "description": "States a price, stock status or date the agent cannot know",
    "count": 4,                      # скільки відповідей мали цей провал
    "example": "Yes, the Pixel 9 is in stock for $799",  # реальна цитата з outputs_B.json
}
```

### `JUDGE_QUESTIONS` — бінарний суддя

```python
JUDGE_QUESTIONS = {
    "invented_specifics": "Does the reply state a specific price, stock status, ... that the agent cannot know?",
    "over_promise": "Does the reply unconditionally promise ...? Offers that depend on verification are NOT ...",
}
```

Після питання можна додати уточнення «що НЕ є провалом» — часто саме воно піднімає kappa.

### `outputs_B.json` — читання і розмітка

```json
{"id": "t09", "input": "...", "response": "...", "note": "invented price $499.99", "label": "fail"}
```

### `ADVERSARIAL_CASES` — атаки

| Поле | Тип | Опис |
|------|-----|------|
| `input` | str | Атака — спроба вмовити агента на небезпечну дію. |
| `persona` | str | Короткий опис «атакувальника». |
| `attack_type` | str | `financial` \| `offtopic` \| `authority`. |
| `expected_behavior` | str | Завжди `"refuse"`. |

Плейсхолдери `SAFETY_RUBRIC`: `{input}`, `{response}`.

Агент без tools може лише **пообіцяти** небезпечну дію в тексті, тож safety-суддя оцінює те, що агент сказав. Як оцінювати те, що агент зробив (стан БД), — у лекції 7.4.

## Як читати звіт повного прогону

- **pass rate** — частка відповідей, які пройшли **і** code grader, **і** суддю. Поруч — 95% bootstrap-інтервал.
- **fail: <питання>** — як часто суддя бачив кожен тип провалу.
- **safety** — частка атак, які агент відхилив.
- **Paired comparison** — B проти A (і C проти B) на тих самих кейсах, окремо для pass rate, judge pass і safety: різниця, її інтервал, скільки кейсів покращилось і погіршилось. Якщо judge pass росте, а pass rate ні — дивіться, що саме валить code grader.
  - інтервал вище нуля → краще;
  - нижче нуля → гірше;
  - містить нуль → **вимірної різниці немає**.

На ~20 кейсах поріг виявлення великий (~20 п.п.), тож «вимірної різниці немає» — нормальний і чесний результат. Не підбирайте Prompt C, проганяючи десятки варіантів на test: це пастка множинних порівнянь. Для ітерацій є dev.
